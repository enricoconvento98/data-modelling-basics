Unified Star Schema

Francesco Puppini & Bill Inmon, 2020

The source model

A normal, normalised shop database. Each measure lives at its own level: freight per order, amount per line, ship_cost per shipment.

Why plain joins go wrong

Fan trap. Joining orders → order_lines repeats the order once per line, so its freight is summed three times.

Chasm trap. Orders and shipments both hang off the customer but are unrelated, so the join pairs every order with every shipment.

Acme100105027

Join all four tables at once and you get 3 × 2 = 6 rows: freight 60, amount 200, ship_cost 36.

The USS star: everything joins only to the bridge

flowchart LR
    C["customers"]
    O["orders"]
    L["order_lines"]
    B(("_bridge"))
    P["products"]
    S["shipments"]
    B -- "_key_customer" --> C
    B -- "_key_order" --> O
    B -- "_key_line" --> L
    B -- "_key_product" --> P
    B -- "_key_shipment" --> S

Every query is FROM _bridge LEFT JOIN table ON table.id = _bridge._key_table. No table is ever joined to another table.

How the bridge is built

A UNION ALL of one stage per table. Each row carries its own key, every key reachable through many-to-one links, and only its own measures.

TOPIC 2

Kimball Star Schema

Ralph Kimball, The Data Warehouse Toolkit

Measurements go into FACT tables, context into DIM tables. The first decision is the grain: what one fact row means. Same shop, three grains, three fact tables sharing three dimensions.

    dim_date ||--o{ fact_order : "order date"
    dim_customer ||--o{ fact_shipment : ""
    dim_date ||--o{ fact_shipment : "ship date"

Either keep freight at order grain in its own fact table, or split it down to the lines with an agreed rule (here, in proportion to amount).

Drill-across fixes the chasm trap

Never join two fact tables to each other. Sum each one separately to the shared dimension, then join the small results.

WITH lines AS (SELECT customer_key, SUM(amount)    amount    FROM fact_order_line GROUP BY 1),
     ords  AS (SELECT customer_key, SUM(freight)   freight   FROM fact_order      GROUP BY 1),
     ships AS (SELECT customer_key, SUM(ship_cost) ship_cost FROM fact_shipment   GROUP BY 1)
SELECT c.customer_name, o.freight, l.amount, s.ship_cost   -- 10, 100, 12
FROM dim_customer c
LEFT JOIN lines l USING (customer_key)
LEFT JOIN ords  o USING (customer_key)
LEFT JOIN ships s USING (customer_key);
fact_order_line JOIN fact_shipment
amount 200 · ship_cost 36
drill-across
freight 10 · amount 100 · ship_cost 12

TOPIC 3

Slowly Changing Dimensions

How a dimension keeps (or loses) history

Acme Ltd starts in Milan and moves to Rome on 1 March 2024. Sales: Acme 100 on 20 Jan, Beta Srl (Turin) 70 on 10 Feb, Acme 50 on 5 Apr. Which city gets the January sale?

Type 1 vs. Type 2

Type 1: overwrite. One row per customer, latest values only.

customer_idcity
1 AcmeRome
2 BetaTurin

Sales by city: Rome 150, Turin 70. The January sale moved to Rome.

Type 2: add a row per version. Each version gets its own surrogate key and validity dates.

skidcityvalid_fromvalid_tocurrent
11Milan2024-01-012024-03-01no
21Rome2024-03-019999-12-31yes
32Turin2024-01-019999-12-31yes

Sales by city: Milan 100, Rome 50, Turin 70. History as it was.

Facts point to the version that was valid on the day

flowchart LR
    S1["sale 1 · 2024-01-20 · 100"] --> V1["sk 1 · Acme · Milan"]
    S3["sale 3 · 2024-04-05 · 50"] --> V2["sk 2 · Acme · Rome"]
    S2["sale 2 · 2024-02-10 · 70"] --> V3["sk 3 · Beta · Turin"]

The lookup runs once, at load: sale_date >= valid_from AND sale_date < valid_to.

Type 6: historical and current side by side

All the types

0ignore the changeoriginal value onlydate of birth, original score

RememberJoin facts to a Type 2 dimension on the surrogate key. Joining on the natural key repeats each sale once per version, which is the fan trap again.
TOPIC 4

Data Vault 2.0

Dan Linstedt · the integration layer, beneath the stars

Every source table is split into three kinds of table, and all of them are insert-only.

roleholdsgets a new row when
HUBunique business keys (customer, order, product)a new key appears
LINKunique relationships between hubsa new relationship appears
SATdescriptive attributes, with historyan attribute value changes

One source table becomes three

The raw vault

erDiagram
    hub_customer ||--o{ link_customer_order : ""
    hub_order ||--o{ link_customer_order : ""

    hub_product ||--o{ link_order_line : ""

        char32 customer_hk PK
        int customer_id "business key"
        timestamp load_dts
        varchar record_source
    }
    hub_order {
        char32 order_hk PK
        int order_id "business key"
    }
    hub_product {
        char32 product_hk PK
        int product_id "business key"
    }
    link_customer_order {
        char32 customer_order_hk PK
        char32 customer_hk FK
        char32 order_hk FK
    }
    link_order_line {
        char32 order_line_hk PK
        char32 order_hk FK
        char32 product_hk FK

    }

        char32 customer_hk PK
        timestamp load_dts PK
        char32 hash_diff
        varchar city
    }
    sat_order {
        char32 order_hk PK
        timestamp load_dts PK
        decimal freight
    }
    sat_product {
        char32 product_hk PK
        timestamp load_dts PK
        varchar product_name
    }
    sat_order_line {
        char32 order_line_hk PK
        timestamp load_dts PK
        decimal amount
    }

*_hk is MD5(business key), so every table can be loaded in parallel. hash_diff is MD5(all attributes): a satellite row is added only when it changes.
